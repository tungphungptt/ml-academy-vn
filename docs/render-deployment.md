# Render deployment and data lifecycle

The Blueprint is for a **new** single-instance Docker service on paid Starter
compute with a paid 1 GB disk. Review Render's current prices before creating it.
No service is created by running the checks below. SQLite does not support
horizontal scaling here; a disk also means deploys have downtime.

## Supported tools and verification

Use Node.js 24 LTS and `npm ci`. `package-lock.json` pins the dependency graph.
Prisma/client stay at 5.20.0. The generator uses Prisma 5's multiline syntax.
Next.js 16.4.3 is on the [Active LTS line](https://nextjs.org/support-policy);
React/DOM are 19.3.1. Async cookies/route parameters and the `proxy` convention
follow the [Next 16 upgrade guide](https://nextjs.org/docs/app/guides/upgrading/version-16).
React 19 uses `React.JSX`; TypeScript strict mode remains enabled.

`katex` is pinned to 0.19.1 for the published trust/prototype-pollution fix.
The npm override makes the Markdown math plugins use the same patched renderer;
a rendering regression test covers this integration. Zod 4.6.7 and tsx 4.23.15
address the Zod collection and esbuild advisories. No audit suppression is used.

```sh
npm ci
npx prisma validate
npx prisma generate
npm run verify
python3 scripts/check_content.py
python3 scripts/audit_spec.py
npm audit
npm run build
docker build -t ml-academy-vn-render-check .
```

For browser tests use an isolated database and start a local production server
with `COOKIE_SECURE=false` for HTTP, then run `npm run e2e`. Install Chromium
with `npx playwright install chromium`, or point
`PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` at a compatible existing Chromium.
Do not run browser tests against a production database.

The onboarding cloud uses an HTTPS proxy and an additional CA. Local Docker
builds can pass the existing HTTP(S) proxy build args and mount that trusted CA
as BuildKit secret `extra_ca`. The secret is used only during npm/build commands,
is not copied into the image, and does not disable TLS or Prisma checksums.
Render's normal builder does not require that local proxy configuration.

## First startup and restarts

- `DATABASE_URL=file:/data/app.db` is an absolute Prisma SQLite URL.
- `LESSON_CONTENT_DIR=/data/lesson-overrides` stores admin Markdown edits.
- `SESSION_SECRET` is generated by Render (at least 32 characters required).
- `COOKIE_SECURE=true` is for Render's public HTTPS endpoint.
- Next binds to `0.0.0.0` and uses `PORT`; Docker CMD is not overridden.
- `ADMIN_EMAIL` and `ADMIN_PASSWORD` are optional and omitted from the Blueprint.
  To create an admin, explicitly provide both securely for a manual seed;
  use a unique password of at least 12 characters. Seed never promotes or
  changes the password/role of an existing account with that email.

On an **empty** database only, startup exclusively creates the SQLite file,
applies the versioned initial migration and seeds the catalog in a transaction.
Prisma 5.20's `migrate deploy` requires that empty file to exist. There is no
`db push`, reset, or data-loss flag in startup. A bootstrap lock prevents
concurrent initialization. A pending marker survives incomplete setup and
requires explicit operator recovery. A stale lock after a crash must only be
removed after confirming that no initializer is running.

On an existing database, startup reads migration history, refuses missing,
unfinished or unexpected migrations, and performs **no migration or seed**.
Manual `npm run db:seed` adds missing courses, modules, lesson slugs and dataset/resource/project records
but never overwrites existing edits, users, admin credentials, notes or progress.
Existing lesson IDs, titles, quizzes, module membership and ordering are retained.
New lessons append to matched modules (stable key, existing lesson anchors, then title).
Back up and review on a database copy before manually adding release content to an existing deployment;
startup never performs this reconciliation. Persistent Markdown overrides take precedence over bundled updates.
See [curriculum audit](curriculum-audit.md) for the 50-to-59 regression test.

For interrupted first setup, inspect the log and back up any created data.
After resolving the cause, `npm run db:initialize -- --resume-bootstrap`
explicitly resumes only a bootstrap with a pending marker. Failed migrations
may first require Prisma's documented operator recovery; they are not silently
resolved by startup.

## Existing databases and future schema changes

Never apply the initial migration to an unverified existing database. Back up
SQLite with an online backup API (including any WAL state) and verify restoration
to a separate database. Also export a copy outside the service's disk.

Test migration commands against that **copy** first. For a legacy database with
no Prisma migration history, compare it to `prisma/schema.prisma`. Explicitly
set the copy's absolute `DATABASE_URL` on **every** command; `migrate resolve`
does not inherit the `--from-url` passed to an earlier `migrate diff` command.
Replace the example path below with the verified disposable copy, never a
production database. Run from the repository root after `npm ci`:

```sh
DATABASE_URL='file:/absolute/path/to/isolated-copy.db' npx --no-install prisma migrate diff --from-url 'file:/absolute/path/to/isolated-copy.db' --to-schema-datamodel prisma/schema.prisma --exit-code
# Only after the comparison above exits 0 (no differences):
DATABASE_URL='file:/absolute/path/to/isolated-copy.db' npx --no-install prisma migrate resolve --applied 20261026000000_initial
```

Validate application reads/writes and restore procedures before scheduling the
production equivalent. If it differs, design and review a separate data
migration; do not reset it.

Future schema changes require reviewed, versioned migrations and a maintenance
window, a tested backup, and an operator-controlled `npm run db:migrate` using
the new release and the mounted disk. Render's pre-deploy commands cannot access
the persistent disk, so the Blueprint intentionally has no pre-deploy migration.
Pending migrations stop normal startup instead of silently changing user data.
Rehearse that maintenance procedure on staging before upgrading an existing service.

## Persistent lessons without hiding bundled content

Keep `/app/content` in the Docker image. Do not mount a blank disk over it.
Only edits/new Markdown files go under `/data/lesson-overrides`. Reads, search,
admin listings and lesson validation all use the overlay first and fall back
to packaged lessons. A redeploy can add new packaged lessons without replacing
admin edits. Catalog, quizzes, labs and other bundled JSON remain release files;
admin CRUD records live in SQLite.

Before replacing an old container, export any edited `content/lessons` directory
to a backup. With that backup available in the new environment and the correct
`LESSON_CONTENT_DIR`, run:

```sh
npm run content:import -- /absolute/path/to/backed-up/lessons
```

The importer skips unchanged bundled files, rejects non-regular files and
preflights conflicting overrides. It never overwrites an existing override.
Keep the backup until imports, search and lesson rendering have been verified.
Back up both SQLite and the override directory thereafter.

## Before creating a Blueprint

Validate `render.yaml` against [Render's current schema](https://render.com/schema/render.yaml.json)
and review the [Blueprint specification](https://render.com/docs/blueprint-spec)
and [disk limitations](https://render.com/docs/disks).
Run `python3 scripts/smoke-container.py ml-academy-vn-render-check` after the build.
It creates and removes its own disposable Docker volume and test accounts.
Confirm the container starts, `/api/health` returns 200 with `{"ok":true}`,
registration works, and a recreated container using the same test disk retains
users, progress and edited lessons. A health check is only configured after
that functional validation; it tests the database connection, not every feature.
The current Blueprint includes `/api/health` following that validation.
